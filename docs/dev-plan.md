# 開発計画

仕様書 `docs/spec.md` の「開発計画」（ステップ0〜10）をベースに、レビュー（`docs/spec-review.md`）で見つかった不足を各ステップへ割り当て、作業単位まで分解したもの。

- 規模の目安：S＝1回の依頼で終わる／M＝2〜3回／L＝4回以上
- 各ステップは「完了条件をテストとして先に書く → 実装 → テストが通る → デプロイ → 実機確認」の順
- ⚠ はレビューで追加した項目

## 全体の流れ

```
P 準備 ─▶ 0 試作 ─[判定:描画方式]─▶ 1 土台・読み書き ─▶ 2 表示・再生 ─▶ 3 移調 ─▶ 4 編集・保存 ─▶ 5 PDF
                                                                                            │
                                                                                     [判定:MVP完成]
                                                                                            ▼
                         9 MIDI ◀─ 8 Googleドライブ ◀─[判定:編曲完成]◀─ 7 大編成 ◀─ 6 半自動編曲
                           │
                           ▼
                        10 OMR
```

## ディレクトリ構成（案）

```
src/
  core/                 # 画面に依存しない純粋なTypeScript（Vitestの対象）
    model/              #   型定義（Score, Note, Project…）、schemaVersion変換
    theory/             #   Pitch・Interval・Fraction・調号・異名同音
    musicxml/           #   MusicXML ⇔ 内部データ（読み込み・書き出しはここだけ）
    transpose/          #   モードA・モードB、単旋律抽出
    edit/               #   編集コマンド（undo可能な操作単位）
    check/              #   音域・演奏性チェック
    arrange/            #   解析・割当・縮約・オクターブ調整（ステップ6〜）
    playback/           #   再生用イベント列の生成（繰り返し展開）
  workers/              # Web Worker（Verovio、移調・編曲計算）
  render/               # 描画ライブラリのラッパ（差し替え可能にする）
  audio/                # Tone.js、サンプル読み込み
  storage/              # IndexedDB、ファイル保存、Googleドライブ
  ui/                   # React画面（screens / components / layouts）
config/
  instruments.json      # 楽器定義（音域・移調・音部記号・音色）
  ensembles.json        # 編成（木管5重奏、後で金管5重奏など）
  thresholds.json       # 警告・編曲判定の閾値
test-assets/
  LICENSES.md           # 素材ごとの入手元・ライセンス・作成ソフト
tests/
  e2e/                  # Playwright（画面・性能）
```

**結果（2026-10-24）**：Verovio＋チャンク描画に決定（PCは全目標を達成、スマホ・タブレットは実機確認待ち）。詳細は `docs/decisions/0001-renderer.md`。

**進み具合（2026-10-24）**：ステップP 済み（運命・アイネ・クライネ・K.331 のCC0データは未入手。代わりの素材で進める）。

## ステップ1：土台とMusicXML読み書き（L）

| 作業 | 内容 |
| --- | --- |
| 1-1 | 本番用プロジェクト作成：Vite/React/TS、ESLint・Prettier、Vitest、Playwright、GitHub Actions（テスト）、Cloudflare Pages（自動デプロイ） |
| 1-2 | `core/theory`：Pitch・Fraction・Interval（度数ベース）・MIDI番号計算・調号 |
| 1-3 | `core/model`：⚠レビューの第2節を反映したschemaVersion 1（音部記号、和音の音ごとのタイ、連符グループ、スラー配列、小節index/表示番号、Direction、passthrough、Project型、楽器定義） |
| 1-4 | `config/instruments.json`：木管5種＋ピアノ＋移調楽器（Aクラ、B♭トランペット、E♭アルトサックス）＋運命に出てくる楽器 |
| 1-5 | MusicXML読み込み（.musicxml / .mxl。zip解凍はfflate）。⚠ `<transpose>` を読んで実音化 |
| 1-6 | MusicXML書き出し。⚠ 移調楽器は記譜音＋`<transpose>`で出力。passthrough要素を戻す |
| 1-7 | 「無視した要素」一覧、読めないファイルの理由表示（形式違い・壊れている・20MB超） |
| 1-8 | ⚠ 往復テストの比較関数（比較する項目を固定：レビュー10-3） |

**完了条件**：3本の素材で「読み込み→書き出し→読み込み」して比較関数が一致。運命の読み込み（解析のみ）がPCで1秒以内。

**結果（2026-10-24）**：完了。
- 往復テスト：テスト素材4曲（MuseScore 3.6 由来3曲＋合成1曲）で「読み込み→書き出し→読み込み」の音符情報が一致。さらに **MuseScore 3.2 で読ませて書き出し直したもの**とも4曲すべて一致（`npm run check:musescore`）
- 読み込みの速さ：合成オーケストラ（18パート・500小節）の解析が、ブラウザのWorker内でPC画面サイズ 約0.6〜0.95秒（目標1秒）
- 作成ソフトの異なるファイルは未入手（MuseScore以外のソフトのMusicXMLを入手したら往復テストに足す）
- 自動デプロイは GitHub Pages（`.github/workflows/pages.yml`。Settings → Pages で有効にする必要あり）。Cloudflare Pages へ移すかは後で決める
- 分かったこと：MuseScore 3.2 は要素間に改行がないMusicXMLで一部のパートを読み落とすため、書き出しは改行・字下げ付きにした

## ステップ3：移調（M〜L）

## ステップ4：音符の編集・元に戻す・端末内保存（L）

| 作業 | 内容 |
| --- | --- |
| 4-1 | `core/edit`：編集をすべて「コマンド」（実行・取り消し）として実装。undo/redo 100回 |
| 4-2 | 音高（半音・音階・オクターブ・異名同音）、音価（⚠上書き方式）、付点、連符化、追加・休符化、和音（polyphonicの楽器のみ） |
| 4-3 | タイ・スラー、記号（強弱・アーティキュレーション・テンポ・練習番号） |
| 4-4 | 範囲操作（コピー・貼り付け・オクターブ移動・別楽器へ移す・範囲の移調）、小節の挿入・削除、拍子・調号の変更 |
| 4-5 | 拍の不足は休符で埋める、超過は赤表示。編集ごとに音域チェックを再計算 |
| 4-6 | 入力：PC（クリック・Shift範囲・キーボード）、タブレット／スマホ（鍵盤パネル・下部ツールバー・始点→終点タップ） |
| 4-7 | ⚠ 単旋律抽出の手直し（音ごとに別声部の音へ差し替え） |
| 4-8 | IndexedDB自動保存（編集後3秒）、⚠`navigator.storage.persist()`、⚠プロジェクトJSONの「ファイルに保存／ファイルから開く」 |
| 4-9 | ⚠ 落ちたあとの復元確認 |

**完了条件**：K.331を10か所編集→書き出し→MuseScoreで一致。リロードしても編集が残る。編集反映がPC 0.2秒・スマホ0.3秒以内（Playwrightで計測）。
