# 検証仕様書

Oct 25, 2026 · 検証担当（Claude Code）

アプリ（楽譜作成・編曲アプリ）が `docs/spec.md` の要求を満たしているかを、**作った側とは別の目で**確かめるための決まりごと。何を・どの順で・どう判定し・どう記録するかを決める。

## 1. 検証者の役割と決まり

| 決まり | 理由 |
| --- | --- |
| 判定の基準は `docs/spec.md`（仕様）。`docs/dev-plan.md` の「結果」は実装側の自己申告として扱い、そのまま合格にはしない | 自己申告をなぞるだけでは検証にならない |
| 既存の自動テストが通ることは**合格の必要条件**だが十分条件ではない。仕様の要求ごとに、既存テストが見ていない点を検証者のテストで確かめる | 作った人と同じ前提のテストは、同じ見落としをする |
| 検証者は製品コード（`src/` `config/` `public/`）を直さない。見つけた不具合は報告書に記録し、直すのは実装側 | 直した人が自分で合格を出すと独立性がなくなる |
| 検証用のテストは `tests/verification/` に置き、既存の `npm run check`・`npm run test:e2e`（CI）には混ぜない | 不具合を示すテストが CI を赤くして開発を止めないように。直ったら実装側が既存テストへ移す |
| 期待値は仕様から先に決めてから実行する（実行結果を見て期待値を合わせない） | 結果に引っぱられないように |
| 確かめられなかったものは「合格」にせず「保留」と書き、理由（実機がない・ツールがない等）を残す | 確かめていないことを確かめたことにしない |

## 2. 検証の対象と環境

- 対象：ブランチ `main` 相当の最新コミット（報告書に commit を記録する）
- 実行環境：Linux のクラウド環境、Node 22、Playwright（Chromium のみ）
- 画面サイズ：PC（1280×800）・タブレット（1024×1366、タッチ）・スマホ（Pixel 7）。既存の `playwright.config.ts` と同じ
- テスト素材：`test-assets/`（CC0）。仕様の候補曲（運命・アイネ・クライネ・K.331）が未入手のため、`docs/dev-plan.md` の代替（合成オーケストラ・K.387・K.464）を使う。代替で確かめたことは報告書に明記する

### この環境で確かめられないもの（保留として扱う）

| 項目 | 理由 |
| --- | --- |
| 実機（iPhone・iPad・Android）の表示・操作感・速さ | 実機がない |
| Safari（WebKit）での動作 | この環境の Playwright は Chromium のみ |
| MuseScore での往復（`npm run check:musescore*`） | `mscore3` が入っていない |
| 再生音が実際に聞こえるか・音色のバランス | 音を聞けない。再生イベント列と画面の反応で代える |
| Googleドライブ保存・共有（ステップ8） | 未実装（`docs/dev-plan.md` に結果なし）。v2 の機能なので「未実装」と記録するだけで不合格にはしない |

## 3. 検証の段階

| 段階 | 内容 | 道具 | 合格の条件 |
| --- | --- | --- | --- |
| L1 静的・単体 | 型・lint・整形・既存の単体テスト | `npm run check` | すべて通る |
| L2 既存の画面テスト | 既存の Playwright を3つの画面サイズで | `npm run test:e2e` | すべて通る。性能の計測値を記録 |
| L3 検証者のロジック検証 | 仕様の要求を純粋関数に対して直接確かめる | `npm run verify:logic`（Vitest、`tests/verification/logic/`） | 要求ごとに判定（下の表） |
| L4 検証者の画面検証 | 仕様の画面・端末の要求を、利用者の操作で確かめる | `npm run verify:ui`（Playwright、`tests/verification/ui/`） | 要求ごとに判定（下の表） |
| L5 実機 | 実機での確認 | 人の手 | この環境では保留 |

## 4. 検証項目（要求との対応）

ID の頭：IO＝読み書き、TR＝移調、RG＝音域、ED＝編集、ST＝保存、AR＝編曲、PB＝再生、PDF＝書き出し、UI＝画面・端末、PF＝性能、DOC＝表示・記載。

### 読み込み・書き出し（仕様「入力」「対応するMusicXML要素」「エラー処理」）

| ID | 要求 | 確かめ方 | 段階 |
| --- | --- | --- | --- |
| IO-01 | MusicXML（.musicxml / .mxl）を読み込み、書き出して読み戻しても音符情報（小節・onset・duration・音高・タイ・連符・声部・staff）、調号・拍子・音部記号が変わらない | 全素材で往復し `diffScores` が空 | L3 |
| IO-02 | 移調楽器は読み込みで実音にし、書き出しは**記譜音＋`<transpose>`** | B♭クラ・E♭ホルンを含む素材を書き出し、XML の `<transpose>` と記譜の音名を見る | L3 |
| IO-03 | 20MB を超えるファイルは理由を出して断る | 20MB+1 バイトのデータ | L3 |
| IO-04 | 形式違い・壊れたファイルは理由を表示する | 壊れた .mxl・XML でないテキスト・PDF | L3・L4 |
| IO-05 | 未対応の要素があっても読み込みを続け、「無視した要素」の一覧を出す | 未知の要素を混ぜた MusicXML | L3・L4 |
| IO-06 | 拍が合わない小節は警告扱いで表示を続ける | 拍の多すぎる小節を含む MusicXML | L3 |
| IO-07 | 読み込み時にパート名・楽器・調号・拍子・小節数を一覧表示 | 確認画面の表示 | L2 |
| IO-08 | 保持のみの要素（歌詞・コード記号・運指など）を書き出しに残す | 歌詞・コード記号を含む MusicXML を往復 | L3 |
| IO-09 | MIDI を読み込める（v3） | 既存テスト | L2 |
| IO-10 | 正しく書かれた楽譜（反復記号で分かれた小節・弱起と対になる最後の小節を含む）は、読み込み確認の既定のまま開いて書き出しても音符情報が変わらない | K.464 を画面で開いてすぐ書き出し、元と比べる | L4 |
| IO-11 | 本当に拍の足りない小節は、隣にも短い小節があっても（反復記号・弱起の印がなければ）拍が合わない小節として警告する | 4/4 で2拍の小節が2つ続く MusicXML | L3 |

### 移調（仕様「移調機能」「移調の細則」）

| ID | 要求 | 確かめ方 | 段階 |
| --- | --- | --- | --- |
| TR-01 | 移調→逆移調で元と**完全一致**（自動置換オフ） | 全12調×全音程（完全・長・短・増・減、1〜8度）×上下、実素材の曲全体 | L3 |
| TR-02 | 自動置換オンのときは実音（MIDI番号）が一致 | ♯7つを超える移調を往復 | L3 |
| TR-03 | 移調後の調が♯・♭7つを超えたら異名同音の調へ（オプションで無効化） | E→G♯（上へ長3度）で A♭ になる／オフで G♯ のまま | L3 |
| TR-04 | B♭クラ譜：Aメジャー→Bメジャー（♯5）、B♭メジャー→Cメジャー | `writtenKey` | L3・L2 |
| TR-05 | 移調楽器の記譜の向き：Aクラ 短3度上、F管ホルン 完全5度上、B♭トランペット 長2度上、E♭アルトサックス 長6度上 | 楽器定義と `writtenPitch` | L3 |
| TR-06 | 記譜調号は記号の少ない方（同数なら♯系）が既定、パートごとに切替可 | 全12調で確認 | L3 |
| TR-07 | 打楽器など音高のないパートは移調しない | 打楽器を含む楽譜を移調 | L3 |
| TR-08 | 小節範囲だけの移調では範囲の頭と直後に調号の変更が入る | 範囲移調後の measures | L3 |
| TR-09 | 曲の途中の転調は調の区間ごとに移調 | 転調を含む楽譜を移調し、各区間の調を見る | L3 |
| TR-10 | 元のパートを複製して楽器を指定（元のパートは残る）。和音パートからは最高音で単旋律を抽出 | `duplicatePartAs` | L3 |
| TR-11 | 実音／記譜の切替がワンタップ | 既存テスト | L2 |
| TR-12 | 「調を指定」の移調が、曲の途中に別の調があっても失敗しない | 全15調→全15調×上下×途中の調15（L3）、転調を含む楽譜を画面で移調（L4） | L3・L4 |

## 5. 判定

| 判定 | 意味 |
| --- | --- |
| 合格 | 仕様どおりに動くことを確かめた |
| 不合格 | 仕様と違う動きを確かめた（不具合として記録） |
| 条件付き合格 | 仕様の要求は満たすが、代替素材での確認・軽微な問題などの条件がある |
| 保留 | この環境では確かめられない（理由を書く） |
| 未実装 | 仕様にあるがまだ作られていない（フェーズが先の機能） |

**リリースの目安**：MVP の項目に「不合格」のうち重大度 S1・S2 が1件もないこと。S3 以下は記録して実装側の判断に任せる。

## 6. 不具合の記録

報告書（`docs/verification/report-*.md`）に、次の形で1件ずつ書く。

| 欄 | 内容 |
| --- | --- |
| ID | `BUG-連番` |
| 重大度 | S1：データが壊れる・消える・落ちる／S2：仕様の機能が使えない・結果が違う／S3：使えるが仕様と少し違う・回避策あり／S4：文言・見た目 |
| 対応する検証項目 | 例：TR-03 |
| 再現手順 | 検証テストの名前と、最小の手順 |
| 期待 | 仕様の該当箇所を引用 |
| 実際 | 観察した結果 |

## 7. 実行のしかた

```sh
npm ci
npm run check            # L1
npm run test:e2e         # L2
npm run verify:logic     # L3
npm run verify:ui        # L4（ビルドしてから画面テスト。3つの画面サイズ）
```

結果は `docs/verification/report-<日付>.md` にまとめる（実行した commit、各段階の結果、項目ごとの判定、不具合、保留の一覧）。
